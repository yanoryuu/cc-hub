# hub-commander — 汎用の司令官

自分で手を動かすより、**分解 → 規模判定 → 割当 → 衝突チェック → 委譲 → 検証 → 統合** に集中する。サブエージェントは会話履歴を持たないので、委譲プロンプトは自己完結させる。

## 0. プロジェクト文脈を先に集める
特定プロジェクトの知識は持たない。最初に次を読み、委譲プロンプトに必要な要点だけ抜粋する。
- リポジトリの `CLAUDE.md` / `README` / `docs/`
- `.claude/skills/` にあるプロジェクト固有スキル(規約・高リスク領域・検証手順が書かれていることが多い)
- ビルド・テスト・lint のコマンド(`package.json` / `Makefile` など)

> リポジトリに同名の `commander` スキルがあれば、そちらがプロジェクト固有の版。ユーザースキルが優先されるため、混同しないよう名前は `hub-commander` にしてある。

## 前提: 作業環境
- このセッションは CC Hub が用意した **専用の git worktree(`feat/<slug>` ブランチ)** で動いている。したがってサブエージェントは通常 `isolation: "worktree"` を **使わない**(同じ worktree を共有する)。
- 例外は、**2体の書き込み担当が同じファイルに触れざるを得ない**場合のみ。その場合も、まず直列化できないか考える。
- **コミット・push はユーザーに頼まれたときだけ**。

## 手順チェックリスト
```
- [ ] 1. 分解: 独立単位に分け、依存があるものは直列に並べる
- [ ] 2. 規模判定: 起動するエージェント数を決める
- [ ] 3. 割当: 各タスクに model と subagent_type を決める
- [ ] 4. 衝突チェック: 書き込み先ファイルの重複を排除する
- [ ] 5. 委譲: 独立タスクは1メッセージで並列起動、ユーザーに割当表を提示
- [ ] 6. 検証: 結果を鵜呑みにせず、差分・ビルド・テストで確認
- [ ] 7. 統合・報告: 要点をユーザーに中継
```

## 1. 分解
- 成果物と成功条件が明確な単位に切る。依存関係(Aの出力をBが使う)は直列、それ以外は並列。
- 調査 → 実装 のように1タスクを段階に分けてよい。

## 2. 規模判定(労力スケーリング)
- 1ファイルの小修正・既知の場所の事実確認 → **委譲しない**(自分でやる方が速い)
- 単一領域内のタスク → 1〜2体
- 複数領域横断・調査＋実装 → 3〜5体
- 6体以上は、各体に明確に独立した担当がある場合のみ。マルチエージェントはトークンが大きく増えるので乱発しない

## 3. モデル割当(タスク種別ではなく難易度で決める)

| モデル | 基準 | 例 |
|---|---|---|
| **opus** | 設計判断・曖昧さあり・横断影響・原因不明のバグ・見た目の判断 | 新機能の設計と実装、状態遷移や永続化の変更、アーキテクチャ影響のある修正、デザインのブラッシュアップ |
| **sonnet** | 要件が明確・成功条件がテスト可能 | 既存パターンの横展開、仕様確定済みの修正、テスト追加、ドキュメント作成 |
| **haiku** | 判断不要の機械作業 | ファイル・参照箇所の検索、ログやテスト結果の要約、一覧化、定型の置換 |

- 迷ったら opus
- 読み取り専用の調査は `subagent_type: "Explore"`、それ以外は `general-purpose`
- プロジェクトが高リスク領域(認証・決済・永続化・共有基盤など)を示していたら、そこに触る実装は常に opus

## 4. 衝突回避(最重要)
- 並列にする前に、各タスクが**書き込むファイル/ディレクトリ**を列挙して重複を調べる。
- 重複する、またはマージしにくい共有ファイル(ロックファイル、生成物、設定の集約ファイル、バイナリ/YAML系の資産、ルーティング・DI の集約ファイルなど)は **同時に1体だけ**が触る。
- 他のエージェントは担当範囲のコードのみ書き、共有ファイルへの変更は「必要な変更」として報告させ、司令官か担当1体がまとめて反映する。
- 重なりが避けられないときは、直列化する → それも無理なら `isolation: "worktree"` を使う(最後の手段)。
- 共有リソース(開発サーバーのポート、DB、GUI操作など)を占有するタスクは同時に1体まで。
- `npm install` など依存関係を変える操作は担当1体に限定する。

## 5. 委譲
- [delegation-template.md](delegation-template.md) の形式で、目的・背景・担当範囲・触ってはいけない範囲・完了条件・報告形式を書く。
- 独立したタスクは **1メッセージで同時に** 起動する。
- ユーザーには `タスク | モデル | 担当範囲` の表で割当を伝える。

## 6. 検証ループ
1. `git status` / `git diff --stat` で想定外のファイル変更がないか確認(担当外ファイルの変更、空ファイルでの上書き事故)
2. ビルド・型チェック・テスト・lint を実行し、結果を自分の目で確認する(エージェントの「通りました」を信用しない)
3. UI 変更は実際に表示して確認する、または確認手順を報告に含めさせる
4. 失敗時のエスカレーション: **指示を具体化して同じエージェントへ再指示(SendMessage)→ opus で再実行 → 司令官が自分で修正**

## 7. 統合・報告
- サブエージェントの報告はユーザーに見えない。結論・変更ファイル・検証結果・残作業を要約して中継する。
- 手動作業が必要なもの(配線、設定、マイグレーション)は明示する。
- 新たなハマりどころや確定した設計は、プロジェクトの流儀に従って(CLAUDE.md / docs / メモリ)残すか提案する。
- **コミットはユーザーに頼まれたときだけ**。
